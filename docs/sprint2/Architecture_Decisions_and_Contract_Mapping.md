## 2. Architecture context and scope

The existing System Vision and Boundary describes one conceptual Student Information System (SIS) with four proposed system roles: Student, Instructor, Student Affairs Staff, and Administrators. The final role-to-operation and role-to-data matrix is still open. The Boundary proposes no external systems for Sprint 1 pending team confirmation; PR #43 likewise identifies no confirmed integrations. No external provider or integration is treated here as present.

The existing OpenAPI contract is provisional and has 12 operations. Its OpenAPI 3.1.0 format is a candidate, `http://localhost:8080` is explicitly a proposed local placeholder, and no live server or deployment is asserted. This update treats JWT Bearer plus server-side `sid` session invalidation as **APPROVED** per the Product Owner approval reported in the request, but `api/openapi.yaml` still labels the bearer policy proposed and does not describe `sid` or return a JWT. `POST /sessions` explicitly has `security: []`; contract alignment is required before adoption. No authentication provider or deployment detail is selected.

Issue #34 covers architecture rationale, logical responsibilities, interfaces, data/API mapping, and NFR implications. This document does not specify an implementation, deployment topology, framework, database engine, or authentication provider, and does not approve a new endpoint. The FR-06 read path in §3 is only a recommendation for review. Logical responsibilities below do not imply separate processes, services, teams, or deployable units.

### 2.2 Candidate dependencies and boundaries

- Protected API operations depend on authentication; authorization additionally depends on role and record relationships. The SRS says checks must be server/API-side, but its permission matrix is OPEN.
- Approved session validation requires the JWT `sid` to identify a server-side session that remains valid; logout invalidates it. Expiry duration is **OPEN – requires confirmation**; the provider and implementation remain unselected.
- Approved registration links are Student→Registration and CourseOffering→Registration; CourseOffering belongs to one Course and one Term. Duplicate prevention is approved; `(studentId, courseOfferingId)` remains a proposed logical uniqueness key pending contract and persistence mapping. Active status, enrollment period, capacity, prerequisites, and other failure semantics remain unresolved.
- A Grade belongs to a Registration through `registrationId`; students receive only published grades. Instructor later-read access is required by the draft SRS, but the recommended endpoint is not part of the current contract and its path/permissions remain open.
- External identity, calendar, payment, and notification systems remain unconfirmed candidates. No integration interface or external dependency is specified.
