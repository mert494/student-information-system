## 2. Architecture context and scope

The existing System Vision and Boundary describes one conceptual Student Information System (SIS) with four proposed system roles: Student, Instructor, Student Affairs Staff, and Administrators. The final role-to-operation and role-to-data matrix is still open. The Boundary proposes no external systems for Sprint 1 pending team confirmation; the merged PR #43 SRS likewise identifies no confirmed integrations. No external provider or integration is treated here as present.

The existing OpenAPI contract is provisional and has 12 operations. Its OpenAPI 3.1.0 format is a candidate, `http://localhost:8080` is explicitly a proposed local placeholder, and no live server or deployment is asserted. PD-01's JWT Bearer/`sid` behavior is approved in the merged SRS, but `api/openapi.yaml` still labels bearer security proposed and does not describe `sid` or return a JWT. `POST /sessions` explicitly has `security: []`; contract alignment is required before adoption. No authentication provider or deployment detail is selected.

Issue #34 covers architecture rationale, responsibilities, interfaces, data/API mapping, and NFR implications. This document selects no technology, database engine, provider, hosting, or physical deployment topology. A separate authorized Instructor grade GET is approved as a capability by PD-04; the suggested route in §3 is only a proposed mapping, not an approved path. The C4 Container view shows candidate runnable boundaries; this does not decide how they are physically deployed.

### 2.2 Candidate dependencies and boundaries

- Protected API operations depend on authentication; authorization additionally depends on role and record relationships. The SRS says checks must be server/API-side, but its permission matrix is OPEN.
- Approved session validation requires the JWT `sid` to identify a server-side session that remains valid; logout invalidates it. Expiry duration is **OPEN – requires confirmation**; the provider and implementation remain unselected.
- Approved registration links are Student→Registration and CourseOffering→Registration; CourseOffering belongs to one Course and one Term. The logical unique key `(studentId, courseOfferingId)` is approved by PD-03; its API identity mapping and physical enforcement remain Pending. Active status, enrollment period, capacity, prerequisites, and other failure semantics remain unresolved.
- A Grade belongs to a Registration through `registrationId` (PD-04). FR-06 requires a separate Instructor GET capability, but the path, schema and access scope remain open. Draft SRS FR-07 states published-only results for a Student; that behavior remains subject to overall SRS acceptance and the current OpenAPI example is contradictory.
- External identity, calendar, payment, and notification systems remain unconfirmed candidates. No integration interface or external dependency is specified.
